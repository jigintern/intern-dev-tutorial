# 「使いやすいUIデザイン」再構成案

この文書は `design/slide.md`（現行48枚）を、プログラミング初学者の学生が理解できる資料に組み直すための案です。
**`slide.md` は変更していません。** 実装するときの設計図として使ってください。

水準と思想は `about-webapp/slide-integrated.md` の冒頭コメントに揃えています。
すなわち PREP・1スライド1メッセージ・40px下限・図が主／文字は補助・たとえは1回だけ・時間配分と削る順番を先に決める、です。

前提としている講義順（`README.md` の TOC 順）:
Webアプリケーション概論 → Git → Claude Code → JavaScript → HTML/CSS → Deno → 通信 → API → **Deno KV** → ログイン → **デザイン（この講義）** → ChatGPT API → チーム開発（スクラム）

つまりこの講義の受講者は、**HTML/CSS・JavaScript・Deno KV をすでに触っており、この直後にチーム開発で自分たちのアプリを作り始めます。**
再構成案はこの位置づけを最大限使います（後述 3-6、および「明日から」のスライド）。

## 1. 調査でわかった設計原則

### 1-1. 結論ファースト（PREP）と、スライド1枚あたりの情報量

| 原則 | 内容 | 出典 |
| --- | --- | --- |
| PREP で章を組む | Point（結論）→ Reason（理由）→ Example（具体例）→ Point（結論）。流れが決まっているので、伝えたい内容から外れにくい。スライドの冒頭に目的・結論を置き、中盤以降で根拠と例を展開すると一貫性が出る | [PREP法とは（Commune）](https://commune.co.jp/magazine/prep-method/) / [PREP法でプレゼンを（Document Studio）](https://studio.virtual-planner.com/prep-method/) |
| 1スライド1メッセージ | 1枚に詰め込むと受講者はどこが重要か分からなくなる。伝えたいことをひとつに絞り、文章より図・表・アイコンで視覚的に整理する | [1スライド1メッセージ原則（デール・カーネギー）](https://www.dale-carnegie.co.jp/library/blog/5976/) |
| 1枚＝1トピックではなく1アイデア | スライドは「1セクション」ではなく「1アイデア」を伝えるように設計する。複数のアイデアが同時に載ると、限られた処理容量を分割させることになる | [How One Topic Per Slide Makes Presentations More Effective](https://slidestack.com/blog/how-one-topic-per-slide-makes-presentations-more-effective) |
| 研修資料の文字量 | 本文24pt以上・色は3色以内。図解とアイコンで言語情報そのものを減らす。「見る→止める→試す」で区切って認知負荷を下げる | [IT研修コース設計ガイド](https://www.docswell.com/s/yukiko_it/KQ2N2V-2026-08-13-104156) / [IT研修講師のための情報を絞る技術](https://www.docswell.com/s/smile_yukiko_it/KGN24M-2026-06-17-133650) |
| 研修スライドの構成 | 伝えたいことをひとつに絞り、ジャンプ率（見出しと本文の大きさの比）を1.5〜2.5倍にすると、一瞬で情報の優先順位が伝わる | [研修資料の作り方完全ガイド](https://www.miricanvas.com/blog/ja/how-to-create-training-materials) |

**この資料への適用**: 各章の1枚目を結論スライドにする。`about-webapp` と同じく「あとで戻ってくる場所」として囲み枠で作る。40px下限は現行の `uncover` テーマならおおむね満たせるが、`section.split` で `font-size: 0.85em` を掛けている箇所（現行11, 12, 24, 31, 32, 37, 38, 41）は実効サイズを実測すること。

### 1-2. 認知負荷とワーキングメモリ

| 原則 | 内容 | 出典 |
| --- | --- | --- |
| ワーキングメモリの上限 | 認知負荷理論（Sweller, 1980年代後半）。ワーキングメモリが一度に保持できるのは若年成人で**3〜5項目**。課題の難易度で上下する | [Using cognitive load theory to improve slideshow presentations](https://researchschool.org.uk/durrington/news/using-cognitive-load-theory-to-improve-slideshow-presentations) |
| 二重の言語入力を避ける | スライドに書いてある文字を読み上げてはいけない。学習者は2種類の言語入力を同時に処理できない | [Chartered College: Using CLT to improve slideshow presentations](https://my.chartered.college/impact_article/using-cognitive-load-theory-to-improve-slideshow-presentations/) |
| 無関係な画像は外部負荷 | 学習を直接支えない画像・装飾は extraneous load になり、学習を抑制する。言葉と図を対応させると、逆にワーキングメモリを肩代わりできる | 同上 / [Overloading on Slides: Cognitive Load Theory and PowerPoint Use](https://www.learntechlib.org/d/28143) |
| スライド4枚目で聞き手は落ちる | 情報密度が高いスライドが続くと、序盤で処理が追いつかなくなる | [Cognitive Load Theory: Why Your Boss Stopped Listening at Slide 4](https://analyticure.com/cognitive-load-theory-presentations/) |

**この資料への適用**: 「一度に増やす新語は3〜5個まで」を章単位の制約にする。現行は第3章で **ビュー／コレクションビュー／シングルビュー／ナビゲーション／レイアウト／ワイヤーフレーム** の6語が7枚のうちに出てくる（現行27〜36）。ここを分割する。
また `design-ui-sample.png`（Figmaの部品見本）は、現行4枚目で「UIは情報の境界」の説明図として置かれているが、境界を説明していない＝この位置では extraneous load。使う位置を変える。

### 1-3. 抽象概念は具体から入る（Concreteness Fading）

| 原則 | 内容 | 出典 |
| --- | --- | --- |
| 具体 → 抽象の順 | まず具体的な表象で学び、その後に具体の要素を段階的に抽象表象へ置き換える（enactive → iconic → symbolic）。**具体→抽象は、抽象→具体より成績がよい**。転移課題の正答率も高い | [Concreteness Fading in Mathematics and Science Instruction: A Systematic Review (ERIC EJ1036777)](https://eric.ed.gov/?id=EJ1036777) |
| なぜ効くか | 具体例には余分なディテールがあり、それが概念を既知のものに「接地」させる。初期学習のあとで余分を削っていくと、一般化と転移ができるようになる | [Concreteness Fading: A Method To Achieve Transfer（The Learning Scientists）](https://www.learningscientists.org/blog/2018/2/1-1) |
| 具体例は複数必要 | 具体例が1つだと、その例に固有の特徴と概念の本質が区別できない | [Concrete vs. Abstract（How We Learn）](https://www.learningscicomm.com/concrete-examples) |

**この資料への適用**: 現行の第3章はほぼ全区間が「抽象の説明 → あとで ToDo で確認」の順になっている（現行17〜19 → 20〜25、現行27〜32 → 33〜34）。とくに `fig-view.svg` / `fig-navigation.svg` は「オブジェクトA／オブジェクトB」という抽象ラベルで、具体物が1つも出てこない。ここは **ToDo の具体を先に見せてから、A/B の一般形に上げる**（＝fading）順に入れ替える。

### 1-4. 演習の前に「手本」を置く（Worked Example / Fading）

| 原則 | 内容 | 出典 |
| --- | --- | --- |
| 初学者には手本が必要 | 初学者に対しては、手本（worked example）を示すほうが、ノーガイドの問題解決より認知負荷が低く定着もよい。初学者は例のうち「解法に必要な特徴」と「たまたまの特徴」を切り分けるのが非常に苦手 | [Exploring the Use of Faded Worked Examples（ERIC EJ1086007）](https://files.eric.ed.gov/fulltext/EJ1086007.pdf) |
| 段階的に手を離す | 完全な手本 → 一部を空欄にした問題 → 自力で解く、の順に支援を減らす（fading）。急に自力にすると容量が足りない | [How Fading Worked Solution Steps Works – A Cognitive Load Perspective](https://link.springer.com/article/10.1023/B:TRUC.0000021815.74806.f6) |

**この資料への適用**: 現行の「やってみよう」2枚（現行20, 40）は、直前が概念説明だけで手本がない。**1行目だけ講師が一緒にやる**スライドを演習の直前に挿す（＝完全な手本 → 残りを自力、の fading）。

### 1-5. 新しい用語をいくつまで出せるか

| 原則 | 内容 | 出典 |
| --- | --- | --- |
| 1回の授業で3〜5語 | 1レッスンで学べる新語はおおむね3〜5語。徹底的に教えるなら3〜5語に絞る | [How Many Vocabulary Words Should I Teach?: Less Really is More（Lexia）](https://www.lexialearning.com/blog/how-many-vocabulary-words-should-i-teach-less-really-more) |
| 既知の文脈の中で1語ずつ | 新語は1つずつ、すでに学習者が知っている文脈の中で導入する。語も概念も未知のときは明示的に教える | [IRIS Center（Vanderbilt）: Vocabulary](https://iris.peabody.vanderbilt.edu/module/rti03/cresource/q3/p07/) |

**この資料への適用**: この講義で覚えて帰る語を**5語に絞る**：**オブジェクト / 属性 / アクション / ビュー（コレクション・シングル）/ ナビゲーション**。
CRUD、ワイヤーフレーム、デザインシステム、UML、4つの基本原則は「名前を出すだけ」に格下げし、覚えさせない（＝`about-webapp` が Deno / Deno KV に対して取っている扱いと同じ）。

## 2. 現行資料の問題点（深刻な順）

スライド番号は現行 `design/slide.md` の通し番号（1=タイトル、48=出典）。
「学生の声」は、その位置で実際に頭の中に浮かぶ文をそのまま書いています。

### 【致命】P1. 講義の主眼「オブジェクトから考えると使いやすくなる」の根拠が2枚しかない（現行11, 12）

現行はこの2枚だけで「機能から直接作ると使いにくい／モノを主役にすると使いやすい」を成立させようとしている。

- **学生の声**: 「たまたまToDoだからでは？」「1手か3手かの差なら、そんなに大事？」「モノを主役って、具体的にどういう作業のこと？」
- 比較の軸が**手数だけ**。調査 1-6 ⑤ の通り、OOUI の説得力は「画面数が減る」「拡張性が上がる」まで含めて出るもの。手数だけでは弱い。
- **「なぜ」が完全に欠けている**。人はなぜオブジェクト先行のほうが使いやすいのか（＝先に対象を選び、あとでやることを決めるのが自然）が一言もない。調査 1-6 ② の通り、乗り越えた解説はここを必ず図で見せている。
- 反例（ATM・券売機）がないので、「じゃあATMは間違いなのか」で止まる（調査 1-6 ③）。
- 現行12の見出しは「**モノ**を主役にすると、使いやすい」だが、`モノ` はここが初出で未定義。`オブジェクト` の定義は2枚あと（現行13）。**結論を言う語が、その語の定義より前にある。**
- 講義の最重要地点なのに、割かれているのは48枚中2枚（約4%）。

### 【致命】P2. `design01.png` が仕様と食い違っている（現行10 vs 11）

- 仕様（現行10）は **見る／追加する／完了にする／書く** の4つ。
- `design01.png` のボタンは **見る／追加／完了／消す** の4つ。
- つまり**仕様にない「消す」があり、仕様にある「書く」がない。**
- **学生の声**: 「消すって仕様に書いてあった？」「書くはどこ行った？」
- 仕様 → UI の対応を見せる講義の、いちばん最初の対応例が壊れている。学生がここで一度でも「対応してないな」と思うと、以降の「仕様から抽出する」全部の信頼が落ちる。
- 加えて現行11の手順「1. 完了を押す 2. 一覧が出る 3. ToDoを選ぶ」は、その一覧画面が図に描かれていない。学生は存在しない画面を想像させられる。

### 【重大】P3. 「ビュー」の定義が今日の改稿で壊れ、2枚あとの説明と矛盾する（現行27 → 32）

- 現行27: 「ビューとは、情報が見える**画面**」「画面には**一覧**と**詳細**の2種類がある」
- 現行32: 「複数のビューを**1つにまとめる**」
- **ビュー＝画面だとすると、「複数の画面を1つにまとめる」が何をすることなのか分からない。** 変更前の版は「ビューとは、ユーザーに情報を表示する**領域**」だったので、1画面に複数のビューを載せる＝まとめる、が成立していた。定義を「画面」に単純化したことで、下流の説明が破綻している（詳細は §2-終盤「失われた情報」）。
- さらに現行27の中で自己矛盾している。「一覧、**フォーム**、詳細ページなど」と3つ挙げた直後に「画面には一覧と詳細の**2種類**がある」。フォームはどっちなのか。
- **学生の声**: 「ログイン画面は一覧でも詳細でもないけど？」「設定画面は？」
- 「2種類がある」という断定は、学生が自分の知っている画面と照合した瞬間に破れる。破れると「この人の説明は自分の知っている世界と合わない」になる。

### 【重大】P4. 「やってみよう」が、直前の説明だけでは手が動かない（現行20, 40）

**現行20（オブジェクト抽出の演習）**
- 直前に聞いたのは「オブジェクトは属性とアクションを持つ」「アクションはつくる・かえる・けす」の2枚だけ。**抽出の手順そのものを教えていない。**
- 調査 1-6 ④ の通り、実務の解説は抽出を「名詞を抽出 → 関係を抽出 → 粒度を揃える → プロパティとアクションを付ける」に割っている。現行にはこの手順が1つもない。
- 何に書くのか（紙／付箋／Figma）、何分か、答え合わせがあるのか、個人かペアかが**すべて書かれていない**。
- **学生の声**: 「抽出って、具体的に何をするの？」「ノートに書くの？」「これ当てられる？」

**現行40（レイアウトの演習）**
- 直前は「レイアウト3種」の紹介2枚と「アクションはオブジェクトの近くに」の見出し1行。ここから**ワイヤーフレームを描け**という要求。
- ワイヤーフレームという語は現行36で「いわゆるワイヤーフレーム」と一度出るだけで、**定義されていない**（調査 1-7：未経験者はここが分からないと明言している）。
- 描く道具が指定されていない。`design04/05/design-ui-sample.png` は Figma の画面だが、**スライド中に Figma という語が1度も出てこない**。`design/README.md` は「ハンズオンを通して」と書いているのに、ハンズオンの手順書がリポジトリに存在しない。
- **学生の声**: 「何で描くの？」「どこまで細かく描くの？」「絵が下手なんだけど」

**ラベルの意味が揺れている**: 現行10は `_class: exercise spec` で「### つくるもの」、現行20と40は同じ `exercise` で「### やってみよう」。同じ見た目のバッジが「これから作る物の提示」と「今すぐ手を動かせ」の両方を指している。

### 5-3. 実装するときの注意

- **`design01.png` の修正が最優先**（P2）。仕様と食い違ったままでは、どんなに構成を直しても第2章の信頼が保てない。

- レンダリング確認は `marp --no-stdin --allow-local-files slide.md --images png -o png/s.png` で全枚数を画像化して目視する。
- CI（`.github/workflows/gh-pages.yml`）は出力名を決め打ちで読む。`design/slide.md` のファイル名は変えない。
- 発表メモ（`<!-- -->`）が現行は0件。**各スライドに【N分】と台本を入れる**こと。`about-webapp` と同じ形式にすれば、誰が話しても同じ講義になる。
- `design/README.md` は「ハンズオンを通して」と書いているが、ハンズオンの手順書が存在しない。**Figma を使うなら、`design/HANDSON.md` を別に用意し、スライドから参照する**（新40・新47の受け皿）。
